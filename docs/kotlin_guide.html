1 Kotlin を読むための最小限

ここだけは先に頭に入れておきます。逆に言うと、これ以外は出てきたときに覚えれば十分です。

1.1 val と var

val a = 10     // 再代入できない（定数のように扱う）
var b = 10     // 再代入できる
b = 20         // OK
// a = 20      // コンパイルエラー

Kotlin では val が既定です。 このリポジトリのコードを検索してみると、var はごく少数しかありません。 「後から変わる値」だけを var にし、それ以外は全部 val にします。

これは好みの問題ではありません。 var が少ないほど「この値はどこで書き換わるのか」を追う必要が減り、 とくに複数のスレッドが絡むこのアプリでは、バグの数がそのまま減ります。

1.2 型は後ろに書く

val name: String = "capture"
val count: Int = 42
val ratio: Float = 1.5f          // Float は末尾に f
val ok: Boolean = true

右辺から型が分かるときは省略できます（型推論）。

val name = "capture"   // String だと分かるので書かなくてよい

ただし関数の引数と戻り値の型は省略できません。ここは必ず書きます。

1.3 関数

fun add(a: Int, b: Int): Int {
    return a + b
}

fun で始め、引数名: 型 を並べ、): 戻り値の型 と書きます。 戻り値がないときは : Unit ですが、省略するのが普通です。

fun log(message: String) {     // 戻り値なし
    println(message)
}

1.4 null とどう付き合うか（Kotlin の中心的な話）

Kotlin では、型は既定で null を入れられません。

val s: String = null      // コンパイルエラー
val t: String? = null     // OK（? を付けた型だけが null を持てる）

これが Kotlin の最大の特徴です。 「値があるかどうか分からない」ことが型に書いてあるので、 うっかり null を触って落ちる、という事故がコンパイル時に止まります。

null かもしれない値を扱う道具が 3 つあります。

?. — null なら何もしない

val n: Int? = s?.length      // s が null なら n も null。s.length は呼ばれない

?: — null ならこっちを使う（エルビス演算子）

val n: Int = s?.length ?: 0  // s が null なら 0

?: は横に倒すと顔文字（エルビス・プレスリーの前髪）に見えるので、この名前です。 右側には return も書けて、この形がコード中に何度も出てきます。

val session = this.session ?: return   // session が null ならこの関数を抜ける

!! — null じゃないと断言する（使わない）

val n: Int = s!!.length      // s が null なら実行時にクラッシュ

!! はこのリポジトリで 1 回も使っていません。 書けてしまいますが、これを書いた瞬間に Kotlin の null 安全は無効になります。 !! を書きたくなったら、?: で早期 return するか、 そもそも null になりうる設計を直すのが正解です。

2 Zip.kt を読む

36 行で、このアプリで一番短いファイルです。 やっていることは「ディレクトリを ZIP に固める」だけ。 なのに、Kotlin らしい書き方がひととおり入っています。

app/src/main/java/com/example/arcorefetcher/capture/Zip.kt
package com.example.arcorefetcher.capture

import java.io.File
import java.io.FileOutputStream
import java.util.zip.ZipEntry
import java.util.zip.ZipOutputStream

/** 撮影セッションのディレクトリを 1 つの ZIP にまとめる（共有シートで渡すため）。 */
object Zip {

    fun zipDirectory(dir: File, target: File): File {
        ZipOutputStream(FileOutputStream(target).buffered()).use { zos ->
            zos.setLevel(1)
            addRecursively(zos, dir, dir.name)
        }
        return target
    }

    private fun addRecursively(zos: ZipOutputStream, file: File, entryPath: String) {
        if (file.isDirectory) {
            zos.putNextEntry(ZipEntry("$entryPath/"))
            zos.closeEntry()
            file.listFiles()?.sortedBy { it.name }?.forEach {
                addRecursively(zos, it, "$entryPath/${it.name}")
            }
            return
        }
        zos.putNextEntry(ZipEntry(entryPath))
        file.inputStream().buffered().use { it.copyTo(zos) }
        zos.closeEntry()
    }
}

2.1 package と import

package はこのファイルが属する名前空間で、ディレクトリ構成と一致させます。 com/example/arcorefetcher/capture/ にあるファイルは package com.example.arcorefetcher.capture です。ここがずれるとビルドが通りません。

import は他の名前空間の型を短い名前で使うための宣言です。 import java.io.File と書いておけば、以降 java.io.File ではなく File と書けます。

同じ package の中（たとえば capture パッケージ内の YuvJpeg や TransformsJson）は import 不要で、そのまま使えます。 CaptureSessionWriter.kt が YuvJpeg を import なしで呼べているのはこのためです。

2.2 object — インスタンスを作らない置き場

object Zip {
    fun zipDirectory(...) { ... }
}

class ではなく object と書くと、実体がひとつだけ自動で作られます （シングルトン）。呼ぶときは Zip.zipDirectory(...) と、型名から直接呼びます。 new に相当するものは書きません（Kotlin に new はありません）。

「状態を持たず、関数を置いておくだけの入れ物」に使います。 このリポジトリでは Zip / PoseMath / YuvJpeg / TransformsJson / CaptureSpec が object です。どれも中に var を持っていません。

Python でいえばモジュールに関数を並べた状態、と考えると近いです。

2.3 private — 外から呼べなくする

zipDirectory には付いていませんが、addRecursively には private が付いています。 これはこのファイルの外からは見えないという意味です。

Zip の利用者に見せたいのは zipDirectory ひとつだけで、 再帰の補助関数は内部の都合です。公開するものを最小にするのは、 あとで実装を変えたくなったときに、外に影響が出ないようにするためです。

2.4 ラムダと it

file.listFiles()?.sortedBy { it.name }

{ it.name } がラムダ式（その場で書く名前のない関数）です。 sortedBy は「各要素から並び替えのキーを取り出す関数」を受け取るので、 「要素の name を使って並べ替えて」という意味になります。

引数が 1 つのラムダでは、引数名を省略して it と書けます。 省略しないで書くとこうです。

file.listFiles()?.sortedBy { f -> f.name }

-> の左が引数、右が中身です。引数が 1 つなら it にできる、というだけの話です。

2.5 末尾ラムダ — 丸括弧が消える理由

ここが初見でいちばん戸惑うところです。

// 本来の形
file.listFiles()?.sortedBy({ it.name })

// 最後の引数がラムダなら、丸括弧の外に出せる
file.listFiles()?.sortedBy() { it.name }

// 引数がラムダだけなら、丸括弧ごと省略できる
file.listFiles()?.sortedBy { it.name }

3 つとも同じ意味です。Kotlin では一番下の形で書くのが普通なので、 なにか { ... } という並びを見たら「関数呼び出しにラムダを渡している」と読みます。

これを知らないと use { ... } や apply { ... } が 言語のキーワードに見えてしまいますが、全部ただの関数呼び出しです。

2.6 use — 閉じ忘れをなくす

ZipOutputStream(...).use { zos ->
    zos.setLevel(1)
    addRecursively(zos, dir, dir.name)
}

ファイルやストリームは、使い終わったら閉じる必要があります。 途中で例外が飛んでも閉じなければならないので、自分で書くと面倒です。

use はブロックを抜けるときに必ず close() を呼んでくれる関数です。 例外で抜けた場合も閉じます。Python の with 文とほぼ同じ役割です。

ここでは引数に zos と名前を付けています（it のままでもよいのですが、 ネストするので名前を付けたほうが読みやすい）。 33 行目のほうは it のまま使っています。

file.inputStream().buffered().use { it.copyTo(zos) }

2.7 ?. の連鎖

file.listFiles()?.sortedBy { it.name }?.forEach { ... }

listFiles() は Java のメソッドで、失敗すると null を返します （ディレクトリが読めないときなど）。 Kotlin から見ると戻り値の型は Array<File>? なので、そのままでは .sortedBy を呼べません。

?. をはさむと「null でなければ呼ぶ、null ならそこで打ち切って全体を null にする」 という意味になります。?. が 2 つ連なっているのは、 listFiles() が null なら sortedBy も forEach も実行されない、という意味です。

1 行で書くとこうなりますが、null チェックを自分で書くとこうです。

val files = file.listFiles()
if (files != null) {
    for (f in files.sortedBy { it.name }) { ... }
}

2.8 文字列テンプレートの実例

zos.putNextEntry(ZipEntry("$entryPath/"))
addRecursively(zos, it, "$entryPath/${it.name}")

変数をそのまま埋めるなら $名前、 式（.name のようにドットが続くもの）を埋めるなら ${ } です。 $entryPath.name と書くと「entryPath を埋めたあとに文字列 .name」になってしまうので、 ドットが続くときは必ず ${ } が要ります。

3 PoseMath.kt を読む

57 行。カメラの姿勢（位置と向き）を、書き出す形に変換するだけのファイルです。 数学の中身は分からなくてかまいません。Kotlin として何が書いてあるかだけ追います。

3.1 配列の型

val m = FloatArray(16)        // Float が 16 個の配列。全部 0.0f で埋まる
val q = FloatArray(4)
val t = FloatArray(3)

Kotlin には配列の型がいくつかあります。

書き方意味
FloatArrayFloat 専用の配列。中身が素の数値で、速い
IntArray / ByteArray / LongArray同じく専用の配列
Array<String>なんでも入れられる配列。<> の中が要素の型
List<String>読み取り専用のリスト。要素を足したり消したりできない
MutableList<String>足したり消したりできるリスト

<> はジェネリクスといって、「中身の型」を指定する書き方です。 List<String> は「String のリスト」。 Array<FloatArray> なら「FloatArray の配列」＝ 2 次元配列です。

3.2 Array(4) { ... } — 初期化ラムダ

return Array(4) { row -> FloatArray(4) { col -> m[col * 4 + row] } }

これが読めれば 3 章は終わりです。分解します。

FloatArray(4) { col -> ... }

FloatArray(4) は「長さ 4 の配列」ですが、 末尾にラムダを付けると「各要素をどう作るか」を書けます（2.5 の末尾ラムダです）。 ラムダには添字 0, 1, 2, 3 が順に渡されるので、 col には 0〜3 が入り、その戻り値がその位置の要素になります。

FloatArray(4) { col -> col * 10f }   // [0.0, 10.0, 20.0, 30.0]

これを二重にすると 2 次元配列が作れます。

Array(4) { row ->              // 4 行つくる。row = 0,1,2,3
    FloatArray(4) { col ->     // 各行に 4 列つくる。col = 0,1,2,3
        m[col * 4 + row]       // 1 次元配列 m から拾ってくる
    }
}

やっていることは「1 次元で並んだ 16 個の数値を、行と列を入れ替えながら 4×4 に並べ直す」です。 ループを書かずに 1 行で書けるのが、この形の利点です。

3.3 単一式関数 — { } を = にする

fun trackingStateOf(name: String): String =
    if (name in TRACKING_STATES) name else "STOPPED"

（これは次章の CaptureModel.kt からの先取りです。 PoseMath.kt の関数はどれも本体が数行あるので、この形になりません。）

本体が式ひとつだけの関数は、{ return ... } ではなく = ... と書けます。 上は次と同じ意味です。

fun trackingStateOf(name: String): String {
    return if (name in TRACKING_STATES) name else "STOPPED"
}

短い関数はこの形のほうが読みやすいので、Kotlin ではよく使われます。

3.4 floatArrayOf — 中身を並べて作る

floatArrayOf(0f, 0f, 0f, 1f)   // 中身を直接書いて配列を作る
FloatArray(4)                  // 長さだけ指定して 0 で埋める

同様に intArrayOf、listOf、setOf、mapOf があります。 CaptureModel.kt に出てくる setOf("TRACKING", "PAUSED", "STOPPED") がその例です。

3.5 早期 return とガード

private fun normalized(q: FloatArray): FloatArray {
    val n = sqrt((q[0] * q[0] + q[1] * q[1] + q[2] * q[2] + q[3] * q[3]).toDouble())
    if (n <= 0.0 || !n.isFinite()) return floatArrayOf(0f, 0f, 0f, 1f)
    return FloatArray(4) { (q[it] / n).toFloat() }
}

0 で割ると壊れるので、先に「おかしい入力」を弾いてから本処理を書きます。 この「異常系を先に return して、あとは正常系だけを書く」形は このリポジトリのあちこちで出てきます。ネストが深くならないので読みやすくなります。

|| は「または」、&& は「かつ」、! は否定です。 .toDouble() / .toFloat() は明示的な型変換で、 Kotlin は Float と Double を勝手に混ぜてくれないので、自分で変換します。

最後の行の q[it] に注目してください。 FloatArray(4) { ... } のラムダ引数を it のまま使っています （{ i -> q[i] / n } と書いても同じ）。

4.1 data class — 値をまとめた型

capture/CaptureModel.kt

    val flX: Float,

これだけで「6 つの値をまとめて持ち運べる型」ができます。使い方はこうです。

== が中身の比較になる、の意味

普通の class だと == は「同じ実体かどうか」になります。 data class だと「中身が同じかどうか」になります。この違いが実際に効いている箇所があります。

capture/CaptureSessionWriter.kt
val override = frame.intrinsicsOverride
    ?: frame.intrinsics.takeIf { it != baseIntrinsics }

「このフレームの intrinsics が、セッション全体のものと違っていたらフレーム側に書く」 という判定です。Intrinsics が data class だからこそ != が中身の比較になり、この 1 行が成立しています。 普通の class にすると、毎回「別の実体」と判定されて全フレームに intrinsics が書かれてしまいます。

copy

meta.copy(originRefreshedAtEnd = false)

meta の他の項目はそのままに、originRefreshedAtEnd だけ false にした 新しい値を作ります。元の meta は変わりません。 val で固めたまま「一部だけ違うもの」を作れるので、書き換えずに済みます。

6.6 文字と文字列は別物

Kotlin は Char と String を厳密に区別します。 'a' は Char、"a" は長さ 1 の String で、== で比べられません。

Kotlin にはスコープ関数が 5 つありますが、実務で使うのは 2 つで足ります。

7.5 sealed class — 種類が決まっている型

private sealed class Task {
    class Write(val frame: PendingFrame) : Task()
    class Finish(val refreshedPoses: List<Pose?>, val onDone: (Result<File>) -> Unit) : Task()
}

ワーカースレッドに投げる「仕事」には 2 種類あります。 「1 フレーム書け」と「締めろ」です。 sealed class は「この型の仲間はここに書いてあるものだけ」と宣言する書き方です。

: Task() が継承（Write は Task の一種である）です。

ありがたみは使う側に出ます。

when (val task = queue.take()) {
    is Task.Write -> ...
    is Task.Finish -> ...
}
  • is は「〜型である」の判定
  • else が要らない。仲間が 2 つしかないとコンパイラが知っているから
  • あとで Task.Cancel を足したら、この when がコンパイルエラーになる

最後のが本質です。種類が増えたときに「対応し忘れた場所」を コンパイラが教えてくれます。else -> {} と書いてしまうと、この恩恵は消えます。

スマートキャスト

is Task.Write で判定した後の枝では、 task は自動的に Task.Write 型として扱われます（スマートキャスト）。 だから task.frame と書けます。明示的な型変換は要りません。

7.6 スレッド — なぜ分けるのか

ここがこのファイルの核心です。

カメラ映像は毎秒 30 回描き直されています。 その描画ループの中で JPEG 変換（数十ミリ秒）とファイル書き込みをやると、 シャッターを切るたびに画面が固まります。

そこで「フレームを預かるだけ預かって、すぐ帰る」ようにし、 実際の変換と書き込みは別スレッドにやらせます。

fun submitFrame(frame: PendingFrame) {
    if (closed) return
    submittedCount.incrementAndGet()
    if (frame.trackingState == "TRACKING") trackingCount.incrementAndGet()
    queue.put(Task.Write(frame))     // 箱に入れるだけ。すぐ帰る
}
private fun runLoop() {              // 別スレッドで、ずっと回っている
    while (true) {
        when (val task = queue.take()) {      // 箱が空なら、来るまで待つ
            is Task.Write -> ...
            is Task.Finish -> { ...; return } // 締めたらループを抜ける
        }
    }
}

LinkedBlockingQueue は複数のスレッドから同時に触っても壊れない箱です。 put で入れ、take で取り出します。 take は箱が空のとき何もせず待ちます（ブロックする）ので、 「仕事が来たか」を自分でぐるぐる確認する必要がありません。

7.7 スレッドをまたぐ値の扱い

複数のスレッドが同じ変数を触ると、ふつうに書くと壊れます。 このファイルには対策が 2 種類出てきます。

@Volatile

@Volatile
private var closed = false

スレッドは高速化のために変数の値を手元に持つことがあり、 あるスレッドが書き換えても、別のスレッドからは古いままに見えることがあります。 @Volatile を付けると、必ず本体を読み書きするようになります。

「読む・書く」だけの単純なフラグに使います。

AtomicInteger

val submittedCount = AtomicInteger(0)
submittedCount.incrementAndGet()

count++ は、見た目は 1 命令ですが実際は「読む → 1 足す → 書く」の 3 段階です。 2 つのスレッドが同時にやると、片方の増加が消えます。

AtomicInteger の incrementAndGet() は この 3 段階が割り込まれないことが保証されています。

@Volatile は「増やす」には使えません。 @Volatile var n = 0 に対する n++ は、やはり壊れます。 「最新の値が見える」ことと「割り込まれない」ことは別の保証です。 読み書きだけなら @Volatile、増減するなら Atomic〜、と覚えてください。

7.9 runCatching と Result

runCatching { } は「ブロックを実行し、例外が出ても投げずに Result に包む」関数です。 try-catch の代わりに使えます。

// try-catch で書くと

    writeFrame(task.frame)
} catch (e: Exception) {

}

Result は「成功したら値、失敗したら例外」を持つ型で、次のように扱います。

.onFailure { }失敗したときだけ実行（it は例外）
.getOrNull()成功なら値、失敗なら null

1 フレームの書き出しが失敗しても、撮影全体は続けたいので、 ログだけ出して次のフレームへ進みます。ここで例外が飛ぶと ワーカースレッドが死に、以降ずっと書き出せなくなります。

8.4 Activity のライフサイクル

Android の画面は、システムから決まった順で関数を呼ばれます。 自分で main から呼ぶのではない、というのが Android の最大の特徴です。

起動      onCreate  →  onResume
他アプリへ            onPause
戻ってくる            onResume
終了                  onPause  →  onDestroy

重要なのは、onPause と onResume は何度でも繰り返されることです。 ホームボタンを押す、通知から別アプリへ行く、画面を消す——全部 onPause が呼ばれます。

カメラのような他のアプリと取り合う資源は、 onPause で必ず手放し、onResume で取り直す必要があります。

override fun onPause() {
    super.onPause()
    if (session != null) {
        // GLSurfaceView を先に止めてから Session を pause する（逆だと
        // 描画スレッドが解放済みの Session を触りうる）。
        binding.surfaceView.onPause()
        session?.pause()
    }
}

コメントに書いてある順序が守るべき点です。 止める順序と始める順序は逆になる、と覚えておくと間違えにくくなります。

ログを見る

Android Studio 下部の Logcat タブで、端末のログが見られます。 検索欄にこのアプリのタグを入れると、自分のログだけ絞り込めます。

Log.i(TAG, "ここまで来た")           // 情報
Log.w(TAG, "怪しい")                  // 警告
Log.e(TAG, "失敗した", exception)     // エラー（例外も一緒に出せる）

println ではなく Log を使います。 TAG は各ファイルの companion object に定義してあります（7.10）。

クラッシュしたら、Logcat の赤い行を上から読むこと。 一番上に例外の種類とメッセージ、その下に「どのファイルの何行目か」が並んでいます。 自分の書いたファイル名（MainActivity.kt など）が出てくる行を探すのが早道です。
